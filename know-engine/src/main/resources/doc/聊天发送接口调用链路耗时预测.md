# `/chat/send` 调用链路耗时预测

## 1. 结论摘要

本文基于 `ChatController#send`、`ChatApplicationService#chat`、RAG 核心模块代码，以及 `know-engine/README.md` 中对 Query Path、流式 RAG、父子分段、三级缓存、引用溯源和卡片事件的说明进行预测。这里的数据是工程估算值，不是压测实测值。

当前 `/chat/send` 的主链路可以拆成两条：

- 非相关问题：会话处理 -> 保存用户消息 -> 意图识别 -> 通用流式回答
- 相关问题：会话处理 -> 保存用户消息 -> 意图识别 -> 问题改写 -> 问题路由 -> 多源检索 -> 父子/兄弟分段扩展 -> BGE 重排 -> 引用回写 -> 最终流式生成

新会话标题生成通过 Java 21 虚拟线程异步执行，不阻塞主响应，但会额外消耗一次 `qwen3.5-flash` 调用和一次会话标题更新。

| 场景 | 首条 SSE 进度 | 首个正文 token | 完整响应 P50 | 完整响应 P90 | 完整响应 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 已有会话，非相关问题，通用对话 | 20-80 ms | 1.6-3.5 s | 5.5 s | 9.5 s | 12.0 s |
| 新会话，非相关问题，通用对话 | 60-180 ms | 1.7-3.8 s | 5.8 s | 10.0 s | 12.5 s |
| 已有会话，相关问题，知识库 RAG | 20-80 ms | 6.0-10.5 s | 13.0 s | 21.0 s | 27.0 s |
| 新会话，相关问题，知识库 RAG | 60-180 ms | 6.1-10.8 s | 13.3 s | 21.5 s | 28.0 s |
| 相关问题，路由到 SQL | 20-180 ms | 6.5-12.5 s | 15.0 s | 25.0 s | 33.0 s |
| 相关问题，路由到 Neo4j | 20-180 ms | 7.0-14.0 s | 16.5 s | 28.0 s | 36.0 s |

相比上一版预测，知识库 RAG 的耗时略上调，主要因为 README 和代码都明确了父子分段回溯、兄弟分段补全、Redis/MySQL 回源、权限/版本过滤、`[REFERENCE]` 输出和可能的 `[CARD]` 输出，这些都会增加少量前置处理和上下文体积。

## 2. 数据量假设

| 数据项 | 预测值 | 说明 |
| --- | ---: | --- |
| 用户问题长度 | 20-120 个中文字符 | 普通汽车咨询、售后、订单或文档问答 |
| 意图识别输入 | 1,000-1,800 tokens | 系统提示词 + 用户问题 |
| 意图识别输出 | 120-260 tokens | `reasoning`、`related`、`intent`、`entities` |
| 标题生成输入 | 80-220 tokens | 仅新会话异步触发 |
| 标题生成输出 | 8-20 tokens | 关闭 thinking 的轻量标题 |
| 问题改写输入 | 1,500-2,500 tokens | 4 维策略：简化、抽象、纠错、车型标准化 |
| 问题改写输出 | 20-80 tokens | 改写后的检索 query |
| 路由输入 | 1,200-2,000 tokens | 三源路由 prompt |
| 路由输出 | 80-180 tokens | `{intent,strategy,confidence}` |
| 初始检索 TopK | 5 条 | 当前 `maxResults(5)` |
| 父子/兄弟扩展后候选 | 5-20 条 | 命中父子分段或兄弟分段时扩大 |
| BGE 重排输入 | 5-20 条 | 取决于扩展数量和路由结果 |
| 最终引用 | 0-5 条 | `ProgressAwareContentAggregator` 聚合后输出 |
| 最终注入上下文 | 2,500-7,000 tokens | 业务 prompt + Top 5 结果 + 父分段完整文本 |
| 最终回答输出 | 300-900 tokens | 中等长度客服回答 |
| `[CARD]` 事件 | 0-3 条 | 车型、订单、召回、对比等结构化场景 |

基础环境假设：

- MySQL、Redis、Elasticsearch、Neo4j 与应用同机或同内网部署
- DashScope 兼容 OpenAI 接口可用，主模型为 `qwen-max-latest`
- 标题模型为 `qwen3.5-flash`，且 `enable_thinking=false`
- Embedding 模型为 `text-embedding-v4`，维度 1536
- BGE-RERANKER ONNX 本地推理，非网络调用
- 数据库连接池、ES 连接、Neo4j 连接、Redis 连接已预热
- 不包含用户公网网络到服务端的传输耗时

## 3. 端到端链路

### 3.1 同步前置处理

| 步骤 | 触发条件 | 数据量 | 预测耗时 |
| --- | --- | ---: | ---: |
| 参数解析 | 每次请求 | `userId`、`content`、`conversationId` | 1-5 ms |
| 创建会话 | `conversationId` 为空 | 1 次 MySQL insert | 20-80 ms |
| 保存用户消息 | 每次请求 | 1 次 MySQL insert | 20-80 ms |
| 返回意图识别进度 | 每次请求 | 1 条 `[PROGRESS]` | 5-20 ms |

已有会话通常 20-80 ms 就能发出首条 SSE；新会话多一次 insert，通常 60-180 ms。

### 3.2 异步标题生成

| 步骤 | 数据量 | 预测耗时 | 是否阻塞主链路 |
| --- | ---: | ---: | --- |
| 构建标题模型和 AI Service | 1 个模型实例 + 1 个代理 | 5-30 ms | 否 |
| 调用 `qwen3.5-flash` | 输入 80-220 tokens，输出 8-20 tokens | 0.6-2.0 s | 否 |
| 回写会话标题 | 1 次 MySQL update | 20-80 ms | 否 |

标题生成本身对端到端响应零阻塞，但高并发新会话会增加 LLM QPS 和数据库写入压力，建议单独限流或复用标题 AI Service。

### 3.3 意图识别

| 步骤 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| 构建 `IntentRecognitionService` 代理 | 1 个代理对象 | 2-10 ms |
| LLM Structured Output | 输入 1,000-1,800 tokens，输出 120-260 tokens | 1.1-3.0 s |
| Java Record 映射 | 1 个 `IntentRecognitionResult` | 5-30 ms |

意图识别运行在 `Schedulers.boundedElastic()`，不会阻塞 WebFlux 事件循环。它是所有分支的共同串行瓶颈。

## 4. 非相关问题链路

当 `related=false` 时，链路跳过 RAG，进入 `CommonChatService.streamChat(userId, content)`。

| 步骤 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| 返回生成进度 | 1 条 `[PROGRESS]` | 5-20 ms |
| 首个 token | 输入 200-1,000 tokens | 0.6-1.6 s |
| 流式生成 | 输出 300-900 tokens | 3.5-8.0 s |

| 分位 | 完整耗时 |
| --- | ---: |
| P50 | 5.5 s |
| P90 | 9.5 s |
| P95 | 12.0 s |

影响因素主要是最终回答长度和模型排队时间。通用分支没有检索、重排、引用回写，整体延迟明显低于 RAG 分支。

## 5. 相关问题 RAG 链路

### 5.1 RAG 管道构建

| 步骤 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| 预存空助手消息 | 1 次 MySQL insert | 20-80 ms |
| 构造 transformer、router、retriever、aggregator、injector | 4 个 retriever，1 个 aggregator | 10-60 ms |
| 获取 BGE-RERANKER 单例 | 已预热 | 1-10 ms |
| 首次加载 BGE-RERANKER | 冷启动 | 0.5-2.0 s |

建议在应用启动后预热 BGE 模型，否则首个 RAG 请求会明显变慢。

### 5.2 问题改写

| 步骤 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| 返回问题优化进度 | 1 条 `[PROGRESS]` | 5-20 ms |
| LLM 改写 | 输入 1,500-2,500 tokens，输出 20-80 tokens | 1.2-3.2 s |
| 异步回写改写结果 | 1 次 MySQL update | 20-80 ms，不阻塞 |

当前改写器返回两个 query：增强 query 和原始 query。后续 route/retrieve 可能按两个 query 执行，最坏情况下会放大路由和检索耗时。

### 5.3 问题路由

| 步骤 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| 返回路由进度 | 1 条 `[PROGRESS]` | 5-20 ms |
| LLM 路由判断 | 输入 1,200-2,000 tokens，输出 80-180 tokens | 1.0-2.8 s |
| JSON 修复与解析 | 1 个路由 JSON | 5-50 ms |

README 提到 JSON 修复管道可处理 Markdown 包裹、中文引号、尾逗号、缺失引号等问题。该逻辑能提升稳定性，但会带来少量 CPU 开销，通常低于 50 ms。

### 5.4 多源检索

| 检索类型 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| 知识库 KNN 检索 | 1 次 embedding + ES Top 5 | 0.8-2.2 s |
| ES 全文检索 | ES Top 5 | 50-200 ms |
| ES 混合检索 | embedding + ES 混合查询 | 0.9-2.5 s |
| SQL 检索 | Text2SQL LLM + 只读 SQL 执行 | 1.5-4.5 s |
| Neo4j 检索 | Text2Cypher LLM + Cypher 执行 | 1.8-5.5 s |

知识库检索不是简单 TopK 返回。`KnowEngineElasticsearchContentRetriever` 会在向量检索命中后做上下文扩展：

| 扩展步骤 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| 兄弟分段补全 | 每个 `brotherChunkId` 触发 1 次 ES filter 查询 | 30-150 ms/组 |
| 父分段替换，Redis 命中 | 每个 `parentChunkId` 读 Redis | 2-20 ms/个 |
| 父分段替换，Redis 未命中回源 MySQL | 1 次 MySQL 查询 + Redis 写入 | 20-100 ms/个 |
| 空值缓存 | 1 次 Redis 写入 | 2-15 ms |

因此，知识库 RAG 的检索阶段建议按 1.0-3.5 s 估算。若命中大量父子/兄弟分段且 Redis 冷缓存，检索阶段可能升至 4-6 s。

### 5.5 重排、引用和卡片

| 步骤 | 数据量 | 预测耗时 |
| --- | ---: | ---: |
| BGE 本地重排 | 5-20 个片段 | 120-900 ms |
| RAG 引用构造 | 0-5 条 `RagReference` | 5-40 ms |
| 回写引用 | 1 次 MySQL update | 20-100 ms |
| 输出 `[REFERENCE]` | 1 条 SSE | 5-30 ms |
| 内容注入 | 2,500-7,000 tokens | 10-80 ms |
| 首个正文 token | 大上下文输入 | 0.9-2.8 s |
| 完整流式生成 | 300-900 tokens | 4.0-10.0 s |
| `[CARD]` 结构化事件 | 0-3 条 | 20-200 ms |
| 回写助手完整内容 | 1 次 MySQL update | 20-120 ms |

`[CARD]` 事件不是每次都有。车型对比、订单详情、召回信息等结构化场景会增加模型输出约束、JSON 解析和前端事件推送，通常只增加 20-200 ms，但会让输出 token 总量变大。

## 8. 高并发容量估算

| 并发请求数 | 通用对话 | 知识库 RAG | SQL/Neo4j RAG | 主要风险 |
| ---: | --- | --- | --- | --- |
| 5 | 稳定 | 稳定 | 稳定 | LLM 响应波动 |
| 20 | 基本稳定 | 可用，延迟上升 | 可用，延迟上升更明显 | LLM QPS、ES/DB 连接、SSE 长连接 |
| 50 | 延迟明显上升 | 高风险 | 高风险 | 多次串行 LLM 调用放大排队 |
| 100 | 不建议 | 不建议 | 不建议 | 模型限流、连接池等待、boundedElastic 堆积 |

RAG 链路的主要瓶颈不是 JVM CPU，而是多次 LLM 串行调用和外部检索依赖。BGE 本地重排会消耗 CPU，但通常不是首要瓶颈。

## 9. 可以做得更好的地方

1. 复用 `IntentRecognitionService`、`TitleSummaryService`、`KnowEngineChatAiService` 代理，避免每次请求重复构建
2. 应用启动时预热 BGE-RERANKER、ES 连接、Neo4j driver、Redis 连接和主模型首包
3. 合并意图识别和问题改写，至少减少 1 次串行 LLM 调用
4. 对明显汽车领域问题使用规则或轻量模型路由，减少 `qwen-max-latest` 路由调用
5. 给父分段 Redis 缓存 TTL 从 30 秒调整为可配置项，高频知识库建议提升到 5-30 分钟
6. 限制兄弟分段扩展上限，例如每组最多补全 3-5 条，避免上下文膨胀
7. 给最终回答设置最大 token 和卡片数量上限，防止 SSE 连接长时间占用
8. 标题生成和改写回写使用独立限流器，避免虚拟线程在新会话高峰无限放大外部调用
9. Text2SQL 执行前增加 SQL 只读校验、LIMIT 注入和字段脱敏耗时埋点，README 已描述安全沙箱，应在指标里体现
10. Neo4j Text2Cypher 失败时如果走 ES 降级，需要记录 `fallback=true`，否则耗时和质量难以复盘
11. 对 `[CARD]` 事件单独统计 `card_count` 和 `card_parse_ms`，避免把结构化输出耗时混进 token 生成
12. 为知识库检索增加 `parent_expand_count`、`brother_expand_count`、`redis_hit_count`、`mysql_backfill_count`，用于解释 RAG 延迟波动
