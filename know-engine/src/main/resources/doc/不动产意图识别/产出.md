## Q3. 网关层是你开发的吗？

**✅ 代码实证**

**面试这么说：**

> 是的，**MCP 工具服务层是我写的**。它本质上就是一个"AI 工具网关"：上游是 LangGraph Agent，下游是 LIFULL 房产 API。这一层做了几件事：
>
> 1. **协议适配**：实现了 JSON-RPC 2.0 的请求解析、工具路由、错误码映射
> 2. **传输层**：支持 stdio（本地调试）、SSE（基础流式）、streamable-http（自研，POST+SSE 双工）三种模式
> 3. **鉴权管理**：OAuth2 Client Credentials 的 token 获取、缓存、过期刷新、并发保护
> 4. **主数据缓存**：启动时预拉地区/线路/站点/户型等主数据，内存索引加速查询
> 5. **工具注册**：将 `property_search`、`property_search_guide`、`synonym_expansion_guide` 注册到 MCP Server

**核心代码：**

MCP Server 启动入口（Go），包含三种传输模式切换：

```go
// Start 使用指定的传输方式启动 MCP 服务器
func (s *MCPServer) Start(ctx context.Context, transportType string, port int) error {
    switch transportType {
    case "stdio":
        return server.ServeStdio(s.server)
    case "sse":
        sseServer := server.NewSSEServer(s.server)
        return sseServer.Start(fmt.Sprintf(":%d", port))
    case "streamable-http", "http":
        // 使用自定义的 streamable-HTTP 传输（自研）
        httpTransport := transport.NewHTTPTransport(port)
        adapter := transport.NewMCPServerAdapter(s.server)
        return httpTransport.Start(ctx, adapter)
    default:
        return fmt.Errorf("unsupported transport: %s", transportType)
    }
}
```

工具注册逻辑：

```go
func (s *MCPServer) registerTools() error {
```

## Q4. 完整的调用链路

**✅ 代码实证**

```
用户浏览器输入自然语言
    ↓
Next.js 前端（CopilotKit Chat 组件）
    ↓ POST /api/v2/copilotkit
Mastra Agent（CopilotRuntime）
    ↓ 模型推理 → 决定调用什么工具
    ↓ MCP 协议 (HTTP)
Go MCP Server（streamable-http 传输层）
    ↓ JSON-RPC 2.0 解析 → 路由到对应 handler
    ↓
SearchPropertiesHandler
    ↓ 参数解析 → 主数据索引查询 → 构建 API 参数
    ↓ OAuth2 Bearer Token（缓存/自动刷新）
LIFULL 房产 API（外部第三方）
    ↓ 返回 JSON 房源数据
    ↓ 逆向回传
Go MCP Server → 结果格式化 → JSON-RPC Response
    ↓
Mastra Agent → LLM 分析结果 → 生成自然语言回复
    ↓
Next.js 前端 → SSE 流式推送给用户（打字机效果）
```

**面试这么说：**

> 一次完整请求的链路：用户在网页输入"想在二子玉川站租个 2LDK，预算 15 万" → CopilotKit 前端把消息发到 Next.js API Route → Mastra Agent 拿到消息后送给 LLM 推理，LLM 判断需要查房，生成 `property_search` 工具调用 → Agent 通过 MCP 协议（HTTP）把工具调用请求发给 Go MCP Server → Go 这边 JSON-RPC 解析后路由到 SearchPropertiesHandler，handler 先查内存索引把"二子玉川"解析成线路站点 ID，把"2LDK"解析成户型代码，把"15 万"转成价格范围，然后拿 OAuth2 token 去调 LIFULL 的房产搜索 API → API 返回房源 JSON → Go 把结果格式化后通过 JSON-RPC Response 返回给 Agent → Agent 把房源数据交给 LLM，LLM 生成"找到了 XX 套房子，推荐这几套……"的自然语言回复 → 通过 SSE 流式推送到前端，用户看到打字机效果的回复。

```go
    var req JSONRPCRequest

    response := t.handler.HandleRequest(&req)

}
```

```go
func (ac *AuthClient) GetToken(ctx context.Context) (*Token, error) {
    // 第一层：检查内存中的当前 token
    ac.tokenMutex.RLock()
    if ac.currentToken != nil && ac.currentToken.IsValid() {
        defer ac.tokenMutex.RUnlock()
        return ac.currentToken, nil
    }
    ac.tokenMutex.RUnlock()

    // 第二层：检查缓存管理器
    if cachedToken, found := ac.cacheManager.GetAuthToken(tokenCacheKey); found {
        if token, ok := cachedToken.(*Token); ok && token.IsValid() {
            ac.tokenMutex.Lock()
            ac.currentToken = token
            ac.tokenMutex.Unlock()
            return token, nil
        }
    }

    // 第三层：请求新 token（带双重检查锁 + 指数退避重试）
    return ac.refreshToken(ctx)
}
```

## Q9. 房产检索怎么做？API？搜索参数？同义词扩展？

**✅ 代码实证**

### 检索流程

调用 LIFULL HOME'S 的 RESTful API（`https://sample-api.homes.co.jp/v1/realestate_article/search`），不是自建搜索引擎。

### 搜索参数

用户口语化输入经过 LLM 结构化后，传给 `property_search` 工具，主要参数：

| 参数 | 说明 | 示例 |
|------|------|------|
| `location` | 地址（5 级格式：町,区,市,县,泛称） | `,渋谷区,,東京,` |
| `station` | 站点+线路 | `二子玉川,田園都市線` |
| `transaction_type` | 租/售 | `rent` / `sale` |
| `property_type` | 物业类型 | `マンション`（公寓） |
| `floor_plan` | 户型 | `2LDK` |
| `rent_price_min/max` | 租金范围（万円） | `10` = 10万日元 |
| `walking_minutes` | 步行距离 | `10`（分钟） |
| `commute_station` + `commute_time_max` | 通勤搜索 | `東京` + `30` |
| `property_conditions` | 特殊条件（同义词扩展格式） | `ペット可,ペット相談可;駐車場あり` |

### 同义词扩展机制（查询扩展）

**核心逻辑：分号 = AND，逗号 = OR，通过 API 实测选最优。**

比如用户说"要能养宠物"，LLM 会扩展为 `ペット可,ペット相談可`（两个同义词用逗号分隔）。Go 后端对每个同义词都发一次最小化搜索请求（`hits=1`），只拿 `totalHits` 数量，选 **命中数最多** 的那个同义词的 ID 作为最终条件。

**面试这么说：**

> 同义词扩展不是靠 Elasticsearch 的 synonym token filter，而是我自己设计的一套"试探式"策略。LLM 负责生成可能的同义词列表（通过 `synonym_expansion_guide` 引导），后端拿到同义词后，逐一发 API 试探查询只取计数不取数据，最终选命中量最大的那个。好处是不依赖额外的同义词词典维护，坏处是多了几次 API 调用，但因为 `hits=1` 所以很快。

**核心代码：**

同义词扩展处理逻辑（Go，核心片段）：

```go
func (h *SearchPropertiesHandler) processPropertyConditions(ctx context.Context, conditions string, ...) []string {
    var conditionIDs []string
    // 按分号切分不同条件组（AND 逻辑）
    conditionGroups := strings.Split(conditions, ";")

    for _, group := range conditionGroups {
        // 按逗号切分同义词（OR 逻辑）
        synonyms := strings.Split(group, ",")
        var matches []synonymMatch

        for _, synonym := range synonyms {
            // 在本地主数据中查找该同义词对应的条件 ID
            results, err := h.propertyLookup.FindPropertyCondition(ctx, synonym)
            if err != nil || len(results) == 0 { continue }

            conditionID := results[0].ID
            // 用最小化 API 调用（hits=1）测试该条件的命中量
            testParams := lifull.PropertySearchParams{
                Hits: 1,  // 只取计数，不取实际数据
                MCF:  []string{conditionID},
            }
            response, _, err := h.lifullClient.SearchProperties(ctx, testParams)
            if err != nil { continue }

            matches = append(matches, synonymMatch{
                synonym: synonym, id: conditionID, count: response.ResultSet.TotalHits,
            })
        }

        // 选命中数最多的同义词
        if len(matches) > 0 {
            bestMatch := matches[0]
            for _, match := range matches[1:] {
                if match.count > bestMatch.count { bestMatch = match }
            }
            conditionIDs = append(conditionIDs, bestMatch.id)
        }
    }
    return conditionIDs
}
```

## Q10. 工具调用为什么会乱序？串行还是并行？

**✅ 代码实证**

### 工具调用方式

**LLM 决定调用顺序**。LLM 一次推理可以输出多个 `tool_calls`，ToolNode 在一轮内批量执行（实际是一个个串行调用 handler，但在同一个节点步骤里完成）。

### 为什么会乱序（这是项目的核心 bug）

问题出在 **CopilotKit 和 LangGraph 的集成**：CopilotKit 框架会往消息列表里插入自己的消息（前端 action 的结果），这些消息和 LangGraph ToolNode 返回的 `tool` 类型消息混在一起后，可能出现 **`tool` 消息前面没有对应的 `tool_calls` 消息** 的情况。OpenAI API 对消息序列有严格要求，看到"孤立的 tool 消息"就直接报 400。

### 解决方案

在 LangGraph 的 `messages` reducer 里加过滤逻辑，遍历所有新增消息，把 `role: 'tool'` 的消息全部移除：

```typescript
const AgentStateAnnotation = Annotation.Root({
  messages: Annotation<BaseMessage[]>({
    reducer: (currentState, updateValue) => {
      const rawMessages = Array.isArray(updateValue) ? updateValue : [updateValue]
      // WORKAROUND: 修复 OpenAI 400 错误
      // "messages with role 'tool' must be a response to a preceding message with 'tool_calls'"
      for (let i = rawMessages.length - 1; i >= 0; i--) {
        if ((rawMessages[i] as any)?.role === 'tool') {
          rawMessages.splice(i, 1)  // 移除孤立的 tool 消息
        }
      }
      return currentState.concat(rawMessages)
    },
    default: () => [],
  }),
})
```

条件路由判断是 MCP 工具还是 CopilotKit action：

```typescript
function shouldContinue({ messages, tools }: AgentState) {
  const lastMessage = messages[messages.length - 1] as AIMessage

  if (lastMessage.tool_calls?.length) {
    const toolCallName = lastMessage.tool_calls?.[0].name
    // 如果是 MCP 工具（不在 CopilotKit tools 列表中），路由到 tool_node
    if (!tools || tools.every((tool) => tool.name !== toolCallName)) {
      return 'tool_node'
    }
    // 如果是 CopilotKit action，直接结束（由前端处理）
  }
  return '__end__'
}
```

**面试这么说：**

> 工具调用本身是 LLM 决定的，一次推理可以生成多个 tool_calls，后端串行执行。**乱序问题不是工具执行顺序的问题，而是消息列表的问题**——CopilotKit 作为前端框架会往对话历史里注入消息，和 LangGraph 的 ToolNode 产生的 tool 响应消息混在一起后，消息序列被破坏了。OpenAI 要求每个 `role: tool` 的消息前面必须有一个带 `tool_calls` 的 assistant 消息，一旦顺序乱了就报 400。我的修法是在状态归并的 reducer 里加了过滤逻辑，把"孤立的 tool 消息"清掉。

##  为什么用 LangGraph？为什么不用 LangChain 链式调用？

**✅ 代码实证**

**面试这么说：**

> **LangChain 的 Chain 是线性**——输入 → 处理 → 输出，适合简单的 RAG 或一次性问答。但我们的场景是**多轮对话 + 条件分支**：用户说的信息可能不够（需要追问），够了才触发检索，检索结果为空还要建议调整条件，这是一个**循环 + 分支的状态图**，Chain 做不了。
>
> LangGraph 把流程建模成 **StateGraph**：
> - `chat_node`：LLM 推理节点
> - `tool_node`：工具执行节点
> - `shouldContinue`：条件路由（有 tool_calls → 走 tool_node；没有 → 结束回复用户）
> - `tool_node → chat_node` 的回边：工具执行完后回到 LLM 继续推理
>
> 这个循环结构让 Agent 可以**自主决定执行几轮**，而不是代码写死流程。比如第一次搜索结果为零，LLM 会在下一轮推理中分析原因并调整参数重新搜索，这完全是 LLM 自己的判断。
>
> 后来迁移到 Mastra 不是因为 LangGraph 技术不行，而是 **LangGraph 平台部署需要商业授权**，Mastra 可以自托管。

**核心代码：**

LangGraph 状态图定义（完整）：

```typescript
const workflow = new StateGraph(AgentStateAnnotation)
    .addNode('chat_node', chat_node)           // LLM 推理节点
    .addNode('tool_node', loggingToolNode)     // 工具执行节点
    .addEdge(START, 'chat_node')               // 入口 → LLM
    .addEdge('tool_node', 'chat_node')         // 工具完成 → 回到 LLM（循环回边）
    .addConditionalEdges('chat_node', shouldContinue)  // 条件路由

// 带检查点的编译（支持状态恢复）
const memory = new MemorySaver()
return workflow.compile({ checkpointer: memory })
```

chat_node 核心逻辑（LLM 推理 + 工具绑定）：

```typescript
async function chat_node(state: AgentState, config: RunnableConfig) {
    const model = new ChatOpenAI({
        apiKey: process.env.AGENT_MODEL_API_KEY,
        configuration: { baseURL: process.env.AGENT_MODEL_BASE_URL },
        model: process.env.AGENT_MODEL_NAME,
    })

    // 将 MCP 工具和 CopilotKit actions 都绑定到模型
    const tools = await getTools()
    const modelWithTools = model.bindTools([
        ...convertActionsToDynamicStructuredTools(state.tools || []),
        ...tools
    ])

    const systemMessage = new SystemMessage({
        content: getPromptForPropertySearch({ userInfo: state.userInfo }),
    })
    const response = await modelWithTools.invoke([systemMessage, ...state.messages], config)
    return { messages: response }
}
```

## Q14. 用什么数据库？有 MQ / Redis 吗？

**✅ 代码实证**

| 组件 | 有/没有 | 说明 |
|------|---------|------|
| **PostgreSQL** | ✅ 有 | Mastra Agent 的 Working Memory 存储 |
| **LibSQL** | ✅ 有（作为 fallback） | 没配 Postgres 时的本地轻量存储 |
| **Redis** | ❌ 没有 | 项目中没有使用 Redis |
| **MQ** | ❌ 没有 | 没有消息队列，所有调用都是同步 HTTP |

**面试这么说：**

> 数据库用的是 **PostgreSQL**（存 Agent Working Memory 和会话状态），作为 fallback 也支持 LibSQL。**没有用 Redis 和 MQ**——因为项目是对话式 AI，每次请求就是一个同步的"推理-工具调用-回复"链路，没有异步任务场景。缓存用的是 **Go 进程内存 + 本地 JSON 文件**（主数据缓存），不需要分布式缓存。如果后续要扩到多实例部署，Redis 是第一个要加的。

**追问"为什么不用 Redis"：**

> 当前是单实例部署，进程内缓存就够了。主数据（地区/线路/站点）在启动时全量加载到内存 map 里，数据量不大（几万条），变更频率极低（每天最多更新一次），没有分布式缓存的必要。

## Q15. 主数据预热怎么做的？

**✅ 代码实证**

### 启动流程

Go MCP Server 在 `main.go` 启动时，**依次确保**三类主数据文件存在：

1. **地理位置数据**：`EnsureLocationDataFiles()` — 都道府县、市区町村
2. **交通数据**：`EnsureStationDataFiles()` — 铁路线路、站点
3. **物业代码**：`EnsurePropertyCodesFiles()` — 户型、物业类型、条件设施码

### 策略

- **首次启动**：调 LIFULL API 全量拉取，序列化为 JSON 文件存到 `./data/cache/`
- **后续启动**：检测文件已存在则**跳过下载**，直接读本地文件
- **加载到内存**：JSON 反序列化后构建 `map[string]XXX` 索引，支持 O(1) 查找 + 模糊匹配



**面试这么说：**

> 主数据预热分三步：**拉取 → 落盘 → 索引**。启动时检查本地 `./data/cache/` 下有没有 JSON 缓存文件，没有就调 LIFULL Master API 全量拉取（地区、线路、站点、户型代码等），拉完序列化成 JSON 文件存本地。后续再启动直接读文件不再调 API。读完文件后在内存里构建 map 索引，后续所有的"用户说二子玉川 → 解析成站点 ID"这种操作都走内存查找，不需要实时调外部接口。



**核心代码：**

main.go 中的启动预热流程：

```go

    mu       sync.RWMutex

    floorPlansData              map[string]lifull.FloorPlan

    floorPlanNameIndex          map[string][]string
    propertyConditionNameIndex  map[string][]string
    propertyTypeDetailNameIndex map[string][]string

// 模糊匹配评分逻辑
func (fm *PropertyFuzzyMatcher) calculateScore(input, candidate string) float64 {
    if input == candidate { return 1.0 }          // 精确匹配
    if strings.HasPrefix(candidate, input) {       // 前缀匹配
        return 0.85 + (float64(len(input)) / float64(len(candidate)) * 0.1)
    }
    if strings.Contains(candidate, input) {        // 包含匹配
        return 0.7 + (float64(len(input)) / float64(len(candidate)) * 0.15)
    }
    return 0.0
}
```
