## 🎯 开场话术：项目整体介绍

> 建议控制在 90 秒以内，语速稳，不要背稿感。

**标准版（推荐）：**

这个项目是我在 Rakuten 参与开发的一个智能房产搜索对话系统，核心目标是让用户可以用自然语言找房子，比如说"想在二子玉川站附近租个 2LDK，预算 15 万"，系统能自动理解意图、调取搜索工具、分析结果，然后给出个性化推荐。

整体架构分两层：前面是AI Agent 层，用LangGraph 搭的，管多轮对话的状态流转；后面是 MCP 工具服务层，用 Go 写的，负责把房产检索、参数引导、同义词扩展这几类能力暴露给模型来调用。两层之间走 MCP 协议通信，支持 stdio、SSE、streamable-http 三种传输模式，本地调试和线上 Web 都能接入。

我主要负责 MCP 服务端和 Agent 编排这两块。MCP 这边我做了工具注册、传输层适配、JSON-RPC 协议封装、OAuth2 鉴权管理，还有主数据的本地缓存和内存索引；Agent 这边主要是 LangGraph 的状态图设计，以及修了一个多框架集成时消息序列错乱导致会话中断的 bug。

整个项目技术栈是 Go + TypeScript，AI 编排用的 LangGraph，模型调用走 OpenAI API，部署通过 GitHub Actions CI/CD 流水线自动化。

### Q1：你怎么理解 MCP？和普通 HTTP 接口有什么区别？

**A：** 普通 HTTP 接口是给人调的，调用时机、参数由开发者硬编码控制。MCP 是专门给大模型设计的工具协议，模型可以自己"发现"有哪些工具、理解每个工具的参数语义、在合适时机自主决定调不调、传什么参数。我做的是把房产检索能力封装成 MCP 工具集，模型对话过程中需要查房子就自己触发，不需要人工干预。

> **追问 1：模型怎么"发现"有哪些工具的？发现机制是什么？**
>
> A：MCP 有标准的 initialize/tools/list 流程。客户端连上 MCP Server 后，会先发一个 `tools/list` 请求，服务端把所有注册的工具名、描述、参数 schema 返回。客户端（一般是 Agent 框架）收到工具列表后，把它转成 LLM 能理解的 function 定义，作为系统提示词的一部分传给模型。模型之后每次推理时，都能"看到"有哪些工具可用，结合用户消息决定要不要调、调哪个。

> **追问 2：参数 schema 是怎么写的？模型怎么知道每个参数填什么？**
>
> A：在 `tools/definitions.go` 里，每个参数用 `mcp.WithString` / `mcp.WithNumber` 等方法定义，带 Description 字段，用自然语言描述参数的含义、格式要求、示例值。这个 Description 最终会变成工具 schema 里的 description 字段，模型推理时会读这些描述生成参数。所以参数描述写得越精确、举例越具体，模型生成的参数质量越高。比如我们的 location 参数描述里明确写了"必须是 5 位数字格式，如 13104"，模型就会照着格式生成，而不是随便传字符串。

> **追问 3：为什么要分三类工具？直接一个 property_search 不行么？**
>
> A：试过，不行，成功率很低。问题在于 LIFULL API 需要日文格式的区域 ID，比如都道府县代码、线路站点 ID，模型不知道这些格式，直接调 property_search 经常传错参数返回空结果。所以我拆了"先引导、再检索"的策略：模型先调 property_search_guide 了解参数格式，再调 synonym_expansion_guide 做词语扩展，最后才调 property_search。三步之后参数质量大幅提升，检索命中率更高。这是系统提示词工程和工具设计结合的结果。

### Q2：注册 Tool 和注册 Prompt 有什么区别？

**A：** Tool 是可以直接执行的能力，模型调用后拿到结构化返回值继续处理；Prompt 是对话模板，适合客户端希望直接渲染引导内容的场景。两种都注册是为了最大化客户端兼容性，Claude Desktop 和自研 Web 客户端接入方式不完全一样，都能支持。

> **追问 1：Prompt 和 Tool 调用的时机有什么不同？**
>
> A：Tool 是模型在推理时主动决定调用的，是"模型触发"的；Prompt 通常是客户端在初始化或特定场景下主动拉取的，是"客户端触发"的。比如用户打开对话界面时，客户端可以先调 MCP 的 `prompts/get` 拉取房产搜索的引导提示，作为初始化上下文；而搜索工具是在用户说出具体需求时由模型自动触发的。两种机制覆盖不同场景，都注册能让客户端灵活选择。

> **追问 2：如果模型调工具传了非法参数怎么处理？**
>
> A：两层保护。第一层是工具定义里的约束，比如枚举类型的参数会限定可选值，必填参数标注 required，模型生成时有约束；第二层是 Handler 里的业务校验，比如 location/station/commute_station 三选一必填，不满足直接返回 `mcp.NewToolResultError`，错误信息是可读的提示，模型收到后会自动追问用户补充信息，不会直接崩。两层配合，即使模型生成了不完美的参数，系统也能优雅降级。

> **追问 3：工具调用链路里，你怎么保证工具执行的幂等性？**
>
> A：从业务角度看，property_search 是纯查询，没有副作用，天然幂等。模型如果调失败了重调，结果一样，不会出现"数据重复写入"之类的问题。工具服务化在我这个场景里主要是读操作，所以幂等性问题比较简单。如果是写操作的工具（比如提交询盘），就需要在 Handler 里加幂等校验，比如用请求 ID 去重。

---

### Q3：MCP 工具注册完了，模型怎么知道什么时候该调？

**A：** 这个是系统提示词（system prompt）控制的。在 `prompt.ts` 里我写了详细的指令，告诉模型：当用户有找房需求时，先调 property_search_guide 确认参数格式，再调 synonym_expansion_guide 扩展搜索词，最后用整理好的参数调 property_search。这相当于给模型写了一套"工作流程手册"。模型会按这个手册执行，不是随机决策。

> **追问 1：系统提示词写不好会有什么后果？**
>
> A：会出现各种奇怪的行为。比如模型跳过引导直接调搜索、参数格式错了、结果为空时不追问用户、或者对不相关的话题也去调搜索工具。提示词工程是我们实际踩坑最多的地方，每次发现模型行为不符合预期，都要回来调整提示词的措辞或顺序。一个有效的提示词应该：明确说明调工具的前置条件、给出具体的调用顺序、提供反例（什么情况下不要调），这样模型的行为才可预期。

```go
func (s *MCPServer) Start(ctx context.Context, transportType string, port int) error {
    switch transportType {
    case "stdio":
        return server.ServeStdio(s.server)
    case "sse":
        sseServer := server.NewSSEServer(s.server)
        return sseServer.Start(fmt.Sprintf(":%d", port))
    case "streamable-http", "http":
        httpTransport := transport.NewHTTPTransport(port)
        adapter := transport.NewMCPServerAdapter(s.server)
        return httpTransport.Start(ctx, adapter)
    }
}

}
```

### Q1：为什么要支持三种传输模式？

**A：** 不同场景接入限制不一样。本地开发和 Claude Desktop 走 stdio，进程间通信，零网络开销；Web 端只能走 HTTP，所以要有 streamable-http；SSE 是历史兼容模式，一些老版本客户端只支持 SSE。三种模式底层工具逻辑完全共用，只是传输方式不同，不用为每种模式重写业务逻辑。

> **追问 1：stdio 模式是怎么工作的？进程间怎么通信的？**
>
> A：stdio 模式下，MCP Server 作为子进程被父进程启动，父进程（比如 Claude Desktop 或 Agent 进程）通过标准输入（stdin）发 JSON-RPC 请求，MCP Server 通过标准输出（stdout）返回结果。底层就是 Unix 的管道，非常简单，不需要网络端口，也不需要处理连接。适合本地工具集成，Claude Desktop 就是这种模式——它启动 MCP Server 进程，然后通过 stdio 和它通信。

> **追问 2：三种模式切换是怎么做的？有没有可能运行时切换？**
>
> A：目前是启动时通过 `-transport` 参数决定，比如 `-transport stdio` 或 `-transport streamable-http`，一旦启动就固定了，不支持运行时切换。如果要运行时切换，理论上可以同时监听多个传输，但 MCP 协议规范里一个 Server 实例对应一种传输模式，混用会有会话状态混乱的问题。实际部署里，本地一个 stdio 实例、线上一个 http 实例，各自独立，更清晰。

> **追问 3：Go 的 goroutine 模型处理高并发连接有什么优势？**
>
> A：Go 的 goroutine 是用户态轻量线程，创建开销极小（初始栈 2KB），可以轻松开几万个 goroutine 同时处理连接，而 Java 的线程默认栈 1MB，开几千个就会内存告警。对于我们的 MCP 服务，每个 SSE 连接对应一个 goroutine 保持长连接，如果并发连接多，Go 的模型完全没压力。另外 Go 的 channel 机制让并发代码写起来更直观，不用手动管理线程池。

---

### Q2：streamable-http 是怎么实现的？

**A：** 核心是 POST + SSE 双工机制。客户端用 POST 发 JSON-RPC 请求，同时用 GET 建立 SSE 长连接等待结果推送。服务端收到 POST 后，通过 Mcp-Session-Id 找到对应的 SSE 连接，把结果推过去。会话靠 UUID session ID 绑定，后台 goroutine 每 5 分钟清理超时 30 分钟的死会话。

> **追问 1：客户端的 POST 请求和 SSE 长连接是同时建立的吗？顺序是什么？**
>
> A：先建 SSE 长连接，再发 POST 请求。流程是：客户端先发 GET 请求建立 SSE 连接，服务端返回一个 session_id 并保持连接；然后客户端每次调工具，用 POST 发 JSON-RPC 请求，Header 里带上这个 session_id；服务端在 session_id 对应的 SSE 连接上推结果。顺序不能反，因为服务端需要先有 SSE 连接才能知道结果往哪推。如果客户端还没建 SSE 连接就发 POST，服务端会返回 session not found 错误。

> **追问 2：SSE 连接断了怎么处理？会丢消息吗？**
>
> A：当前实现里，SSE 连接断了，服务端不会主动重推。客户端需要重新发 GET 建立新会话，再重发请求。不会"自动恢复"，是有意为之的，因为 MCP 的工具调用是无状态的，每次调用都是独立的，重发请求会重新执行工具，结果是一样的（查询是幂等的）。如果是有状态的操作，就需要做消息持久化和重推机制，但当前业务场景不需要。

> **追问 3：SSE 推送和 HTTP 长轮询有什么区别？**
>
> A：HTTP 长轮询是客户端发请求，服务端等到有数据了才返回，客户端收到响应后立刻再发一个新请求，本质上还是客户端驱动的，有延迟和资源消耗。SSE 是服务端推送，客户端建立一个长连接，服务端随时可以主动推数据，客户端不需要重复发请求，延迟更低，连接数也更少。SSE 的缺点是单向的（只能服务端推客户端），但 MCP 的场景正好适合——客户端用 POST 发请求，服务端用 SSE 推结果，两个方向分开走。

### Q3：会话管理怎么做的？

**A：** 每个会话有 UUID session ID，绑定在 Mcp-Session-Id header 里。服务端维护 `map[sessionID]*httpSession`，记录创建时间和 SSE 连接。后台 goroutine 每 5 分钟扫一次，超过 30 分钟没活动的关闭 SSE 连接并清理，防内存泄漏。

> **追问 1：为什么选 30 分钟超时？这个值是怎么定的？**
>
> A：是根据业务场景估的。用户找房一般一次对话持续 10-20 分钟，30 分钟足够覆盖绝大部分正常会话，又不会让僵尸会话占用太久资源。如果超时设太短，用户稍微停顿一下就会话失效，体验差；设太长，长时间不活跃的连接占资源。30 分钟是个经验值，生产上可以根据实际使用数据调整。

> **追问 2：cleanupSessions 的 goroutine 会不会和主请求并发冲突？**
>
> A：不会，因为 sessions map 操作用了互斥锁保护。每次读写 sessions map 都要先拿锁，cleanupSessions 删会话的时候也要拿锁，所以不会和正在处理请求的 goroutine 冲突。Go 里对 map 的并发操作是需要显式加锁的，不加锁会有 data race，我们用 `sync.RWMutex` 解决了这个问题。

```go
            Result:  map[string]interface{}{},
        }
    }
    reqData, _ := json.Marshal(req)
    result := a.mcpServer.HandleMessage(ctx, reqData)
    ...
}

const (
    ParseError           = -32700
    InvalidRequest       = -32600
    MethodNotFound       = -32601
    InvalidParams        = -32602
    InternalError        = -32603
    ToolNotFound         = -32001   // 自定义扩展
    InvalidToolArguments = -32002   // 自定义扩展
)
```

### Q1：为什么要自己写适配层？

**A：** SDK 只支持 stdio 和基础 SSE，不支持 streamable-http，传输层必须自研。但工具执行逻辑复用 SDK 就好，不用重造。MCPServerAdapter 做桥接：把自研传输层收到的 JSON-RPC 请求格式，转换成 SDK 内部格式，再把 SDK 的返回转换回去。

> **追问 1：适配器模式的核心思想是什么？你为什么用它？**
>
> A：适配器模式的核心是"接口转换"，让两个不兼容的接口可以协作，不改变双方的内部实现。我用它是因为：自研传输层有自己的 JSONRPCRequest/Response 结构，mcp-go SDK 有自己的内部格式，两者不兼容但我需要让它们协作。适配器就是中间的"转换头"，外面我的格式，里面 SDK 的格式，两边各自不需要改动。

> **追问 2：你遇到了 SDK 版本的 bug，一般怎么处理这类问题？**
>
> A：分情况。如果 bug 有官方修复计划，等下一个版本升级就行。但如果 bug 影响当前功能而且短期没修复，就需要自己 workaround。我的处理是在适配器层拦截有问题的方法，直接返回 mock 的成功响应，等于绕过 SDK 的 bug 路径。这个 workaround 写了注释记录原因和 SDK 版本，方便以后 SDK 升级后清掉。另外我也会去看 SDK 的 issue 列表，确认这是已知 bug 还是我用法有问题。

> **追问 3：JSON-RPC 2.0 你了解多少？能说一下请求和响应的结构么？**
>
> A：JSON-RPC 2.0 的请求结构是固定的四个字段：`jsonrpc` 固定值 "2.0"；`method` 调用的方法名，比如 "tools/call"；`params` 参数对象或数组；`id` 请求标识，用来配对请求和响应。响应结构是：`jsonrpc` "2.0"；`id` 和请求对应；然后成功时有 `result` 字段，失败时有 `error` 字段，两者互斥。error 里有 `code` 数字错误码和 `message` 描述。-32700 到 -32600 是标准协议错误段，-32000 以下是自定义扩展段，我扩展了 ToolNotFound 和 InvalidToolArguments 两个。

```typescript
const workflow = new StateGraph(AgentStateAnnotation)
  .addNode('chat_node', chat_node)
  .addNode('tool_node', loggingToolNode)
  .addEdge(START, 'chat_node')
  .addEdge('tool_node', 'chat_node')
  .addConditionalEdges('chat_node', shouldContinue)

// 条件路由
function shouldContinue({ messages, tools }: AgentState) {
  const lastMessage = messages[messages.length - 1] as AIMessage
  if (lastMessage.tool_calls?.length) {
    return 'tool_node'
  }
  return '__end__'
}
```

### 状态流转图

```

  ↓
chat_node (LLM 决策)
  ↓ shouldContinue
  ├── 有 tool_calls → tool_node (执行工具) → chat_node (循环)
  └── 无 tool_calls → __end__ (返回用户)
```

### Q1：为什么用 LangGraph，不直接写循环？

**A：** 两个核心原因。一是状态管理，直接写循环要自己维护状态变量，多轮对话一复杂就容易出 bug；LangGraph 把状态显式建模，每一步输入输出都有类型约束，状态变化可追踪。二是扩展性，现在两个节点，以后要加新节点直接 addNode，不用改现有逻辑；如果是 if-else 循环，加一个分支可能要改好几处。

> **追问 1：状态图和普通的有限状态机有什么区别？**
>
> A：传统有限状态机的状态通常是枚举值，比如"待机/运行/错误"，状态是离散的有限集合，转换规则是确定的。LangGraph 的"状态"更宽泛，是一个包含消息列表、用户信息、工具列表等字段的对象，转换规则是由 LLM 的输出决定的，是非确定性的。而且 LangGraph 允许带环（chat_node → tool_node → chat_node），传统 FSM 通常是 DAG。这种设计更适合 AI Agent 场景——流程不是提前写死的，是模型根据上下文动态决定的。

> **追问 2：LangGraph 和 LangChain 什么关系？有什么区别？**
>
> A：LangChain 是工具集合，提供 LLM、工具、链的封装，但控制流是线性的，链跑完就结束。LangGraph 是在 LangChain 之上的编排框架，解决需要循环、条件分支、状态持久化的场景。我的场景需要"调工具 -> 看结果 -> 决定是否再调 -> 循环"这种带回环的流程，只能用 LangGraph，LangChain 的 Chain 做不到。简单说：LangChain 是工具箱，LangGraph 是流程引擎。

> **追问 3：shouldContinue 函数里你怎么判断模型是否要调工具？**
>
> A：检查最后一条消息是否有 `tool_calls` 字段。OpenAI 的协议里，如果模型决定调工具，返回的 AIMessage 里会有 `tool_calls` 数组，里面包含工具名和参数；如果模型决定直接回复用户，`tool_calls` 是空数组或 undefined。我的 shouldContinue 就是检查这个字段，有值就路由到 tool_node，没有就结束。这个判断逻辑非常简单，因为这个决策是模型做的，我只是根据模型的意图来路由。

> **追问 4：多轮对话下，消息历史是怎么保持的？会不会越积越长？**
>
> A：消息历史存在 AgentStateAnnotation 的 messages 字段里，每轮对话追加，MemorySaver 按 thread_id 持久化。确实会越来越长，这是一个真实问题。我们通过系统提示词控制模型只看最近的上下文，但本质上消息列表没有做截断。生产级别的处理应该加 token 计数，超过阈值时做摘要（summarization）压缩历史消息，把多条历史消息压缩成一条摘要，保持上下文在 token 限制以内。这是一个后续优化点，当前演示系统里单次会话不会太长，暂时没问题。

---



### Q2：chat_node 和 tool_node 分别干什么？

**A：** chat_node 负责调 LLM，把消息列表和系统提示词传给 OpenAI，拿到模型响应。tool_node 负责实际执行工具，把工具结果作为 ToolMessage 追加到状态里，然后回到 chat_node。两个节点配合实现自动的多轮工具调用。

> **追问 1：tool_node 里如果有多个工具同时被调用，是串行还是并行执行的？**
>
> A：LangGraph 默认的 ToolNode 对多个 tool_calls 是并行执行的，用 Promise.all 同时跑。这对查询类操作没问题，因为各个工具调用互相独立。我们的场景里，模型一般一次只调一个工具（先调引导，再调搜索），并发不并发影响不大。但如果模型一次调了多个工具，并行执行能减少总耗时。

> **追问 2：工具执行失败了，流程怎么走？**
>
> A：tool_node 会把工具的错误信息包装成 ToolMessage 追加到消息列表里，然后流程回到 chat_node，让模型看到错误信息后自己决定下一步——可能是换参数重试，也可能是告诉用户查询失败了。整个错误处理是"模型驱动"的，不需要在代码里硬编码 retry 逻辑，模型自己会根据错误信息做判断，这是 LLM Agent 相比传统自动化的优势之一。

> **追问 3：MemorySaver 持久化的是什么？服务重启会丢么？**
>
> A：MemorySaver 把每个 thread_id 的完整 Agent 状态（包括 messages、userInfo 等）存在内存里，服务重启会丢。适合开发和演示场景。生产级别应该用 LangGraph 提供的 PostgresSaver 或 RedisSaver，把状态持久化到数据库里，重启不丢历史。这个是架构层面的 TODO，当前版本用内存够用，后续可以无缝切换，因为 LangGraph 的 checkpointer 是可替换的。

### Q1：你碰到了什么 bug？现象是什么？

**A：** 会话偶发中断，不是每次都复现，大概调了几轮工具之后会突然报 400 错误，错误信息是 "messages with role tool must be a response to a preceding message with tool_calls"。看了 OpenAI 文档确认，tool 消息必须紧跟在 assistant 的 tool_calls 后面，不能单独出现。

> **追问 1：这个 bug 为什么是"偶发"的？在什么情况下会触发？**
>
> A：偶发是因为触发条件和操作顺序有关。CopilotKit 的前端 action 机制会在特定时机（比如用户切换对话、前端 action 执行完）往 Agent 状态里 inject 消息，这个注入和 LangGraph 的 tool 消息归并是两个异步流程，当时序刚好错位时，tool 消息会出现在没有配对 tool_calls 的位置。不是每次都触发，是因为大部分时候时序没错，只有在特定网络条件或特定操作节奏下才会触发。这种偶发 bug 是最难排查的，因为你不能稳定复现。

> **追问 2：你是怎么定位到根因的？排查过程说一下。**
>
> A：分三步。第一步，看报错定方向：400 错误信息明确说了是消息序列问题，确认是 messages 数组顺序出了问题，不是参数问题或网络问题。第二步，加日志复现：在 reducer 函数里把每次状态更新时 messages 的完整内容都打出来，包括每条消息的 role 和 id，等待 bug 再次触发。第三步，对比异常日志：触发 bug 时，在日志里看到了一条 role 为 tool 的消息，但它前面没有配对的 role 为 assistant + tool_calls 的消息，是"孤立"的。往上追这条消息的来源，发现是 CopilotKit 的 action 注入的，不是 tool_node 正常流程产生的，时序和 LangGraph 的消息归并冲突了。

> **追问 3：修法是什么？为什么选这个位置修？**
>
> A：在 messages reducer 里加过滤逻辑，每次状态更新时检查新消息里有没有"孤立 tool 消息"，有的话删掉再 concat。选 reducer 这个位置是因为它是一个唯一的状态入口，所有消息归并都要经过它，在这里拦截"一次改，处处生效"，不需要到处改代码。当时也考虑过在 tool_node 里处理，但那样只能覆盖 tool_node 产生的消息，CopilotKit 注入的消息不走 tool_node，覆盖不到。

> **追问 4：这样删消息会不会有副作用？正常的工具结果会不会被删掉？**
>
> A：不会。关键在于正常的工具结果传递路径不同：tool_node 执行完工具后，结果是先作为 ToolMessage 正常产生，前面一定有配对的 AIMessage + tool_calls，这种"配对的 tool 消息"不在我的过滤范围内。我只删"前面没有 tool_calls 配对的孤立 tool 消息"。另外为了保险，加了详细的 warn 日志，每次过滤都会打印被删消息的详情，方便后续 review 确认没有误删正常消息。

> **追问 5：这个修法是最优解么？有没有更好的方案？**
>
> A：这是一个 workaround，不是从根本上修复。更好的方案是在 CopilotKit 侧修正 action 注入消息的时机，确保 inject 的消息不会破坏 tool 序列的约束。但那需要修改 CopilotKit 框架的逻辑，成本高，而且框架升级可能会覆盖修改。当前的 reducer 过滤是防御性的——不管上游怎么注入消息，到我这一层必须保证序列合法。作为一个 workaround 它解决了问题，代价是丢弃了一些"孤立 tool 消息"，但这些消息本来就是非法的，丢了不影响业务正确性。

**A：** 把字符串传给 LocationLookup 服务，里面有全日本地区名称到 ID 的内存索引，做名称匹配，找到对应 city_id，填入 CityIDs。站名就走 TransportLookup 找 linestation_id，填到 LinestationIDs。对模型完全透明，ID 解析全在 Handler 里。

### Q1：为什么不直接每次查 LIFULL API，要做本地缓存？

**A：** 三个原因：性能（本地 map O(1) vs API 几十到几百毫秒）、稳定性（主数据变化频率低，不需要每次实时取，外部抖动不影响）、成本（LIFULL API 有调用频率限制）。

> **追问 1：本地 JSON 缓存 vs 用 Redis 缓存，你为什么选 JSON 文件？**
>
> A：这个项目里 MCP Server 是单实例的，不需要分布式缓存共享数据，本地文件够用，而且不引入额外依赖（不用部署 Redis）。JSON 文件在启动时一次性加载到内存 map 里，之后所有查询都走内存，文件 I/O 只在预热阶段发生一次。如果是多实例部署，各实例有各自的本地文件，也能独立工作，不需要同步。如果数据更新频率高、或者需要多实例共享最新数据，才有必要用 Redis。

> **追问 2：内存索引什么时候建立的？预热时就建好还是懒加载？**
>
> A：启动时就建好，在 LocationLookup 的 Initialize 函数里，依次加载 JSON 文件，把数据放进 map 并建立名称索引。不是懒加载，因为懒加载的话第一次请求会有冷启动延迟，而且要处理并发初始化的问题（双重检查锁）。启动预热虽然让启动时间稍微长一点，但保证了运行期每次查询都是 O(1) 的稳定延迟，这个 trade-off 是值得的。

> **追问 3：map 索引里的数据和 JSON 文件里的数据是什么关系？改了文件会实时更新吗？**
>
> A：不会。服务启动时把 JSON 文件加载进内存，之后的查询全走内存 map，文件改了不会自动同步到内存。如果要更新数据，需要重启服务，重启时再次加载文件。这是刻意的设计：主数据不频繁变，一致性要求不高，重启就能完成更新，不需要热加载。如果要加热加载，需要在 Lookup 服务里加文件 watcher，监听文件变化后加写锁更新 map，复杂度会高很多。

> **追问 4：数据量大概是多少？内存占用有没有估算过？**
>
> A：日本全国有 47 个都道府县、2000 多个市区町村、几万个车站。按每条记录 1KB 估算，全量主数据大概几十 MB。实际内存占用要高一些，因为 Go 的 map 有额外的桶和指针开销，但整体在 100-200MB 以内，对现代服务器来说完全可接受。这是内存换查询速度的经典 trade-off。

```go
            "raw_body", string(bodyBytes))
        return fmt.Errorf("LIFULL API error: %s", lifullErr.String())
    }
    slog.Info("LIFULL API call successful", "endpoint", endpoint, "status_code", resp.StatusCode)
}
```

### Q1：外部 API 挂了对用户有什么影响？怎么处理的？

**A：** makeAPICall 里统一处理错误路径：非 200 解析错误体，通过 fmt.Errorf 往上传。Handler 包装成 MCP ToolResultError，模型告诉用户"查询失败请稍后重试"，不暴露底层错误，不崩会话。

> **追问 1：错误归一化的好处是什么？**
>
> A：把所有外部 API 的错误都收敛到统一的 error 接口，上层代码不用区分"是超时还是 500 还是 401"，统一处理就行。另外统一格式的错误信息对日志分析友好：每条错误日志都有 endpoint、status_code、raw_body，格式一致，可以用脚本批量统计哪个接口失败率高。如果每个调用点各自拼错误信息，格式不一，分析起来很麻烦。

> **追问 2：为什么当前没有做重试？如果要加重试，你会怎么加？**
>
> A：没加是因为权衡后觉得当前阶段不需要——演示系统对可用性要求不高，超时兜底够用。如果要加，应该区分错误类型：5xx 和超时可以重试（服务端临时故障，重试有意义）；4xx 不重试（参数错误，重试结果一样）；401 有专门的 token 刷新机制处理。重试要加指数退避，比如第一次等 1s，第二次等 2s，避免集中请求压垮对方服务。最大重试次数设 3 次左右，超过就直接返回错误。这些逻辑放在 makeAPICall 里，业务层不感知。

> **追问 3：超时时间 30s 是怎么定的？太长会有什么问题？**
>
> A：是参考 LIFULL API 文档和经验设的，正常查询 1-2s，极端情况下可能到 10s。30s 足够覆盖正常慢查询，又不会让 goroutine 无限等待。太长的问题：如果 API 卡死，goroutine 会等 30s 才释放，这段时间内新请求进来也要等，相当于级联阻塞；太短会把正常慢查询也超时掉，影响用户体验。30s 是个经验权衡，实际应该根据 API 的 P99 延迟来设。

```go
func (ac *AuthClient) GetToken(ctx context.Context) (*Token, error) {
    ac.tokenMutex.RLock()
    if ac.currentToken != nil && ac.currentToken.IsValid() {
        defer ac.tokenMutex.RUnlock()
        return ac.currentToken, nil
    }
    ac.tokenMutex.RUnlock()

    if cachedToken, found := ac.cacheManager.GetAuthToken(tokenCacheKey); found {
        if token.IsValid() { return token, nil }
    }
    return ac.refreshToken(ctx)
}

// refreshToken - 写锁 + 双重检查 + 指数退避重试
func (ac *AuthClient) refreshToken(ctx context.Context) (*Token, error) {
    ac.tokenMutex.Lock()
    defer ac.tokenMutex.Unlock()
    if ac.currentToken != nil && ac.currentToken.IsValid() {
        return ac.currentToken, nil  // 双重检查
    }
    for i := 0; i <= ac.config.MaxRetries; i++ {
        resp, err = ac.httpClient.Do(req)
        if err == nil { break }
        time.Sleep(time.Duration(i+1) * time.Second)
    }
}

// 提前 5 分钟预判过期
func (t *Token) IsExpiringSoon() bool {

}
```

### Q1：OAuth2 Client Credentials 和 Authorization Code 区别？你为什么用 Client Credentials？

**A：** Authorization Code 是有用户参与的场景，要跳转授权页，用户同意后才换 token，代表用户操作。Client Credentials 是服务间通信，没有用户参与，直接用 client_id + client_secret 换 token。我的场景是 MCP 服务端访问 LIFULL API，没有用户授权步骤，用 Client Credentials 是正确选择。

> **追问 1：OAuth2 一共有哪几种授权方式？各自适用什么场景？**
>
> A：标准的有四种。Authorization Code：最常用，有用户参与，适合第三方应用代表用户操作（比如"用 Google 登录"）；Implicit：简化版 Authorization Code，直接返回 token，适合纯前端 SPA，但不安全已被废弃；Client Credentials：服务间通信，无用户参与，适合后端调后端（我用的这个）；Password Credentials：直接传用户名密码换 token，安全性差，一般不推荐。还有一个 Device Code，适合 TV 等无浏览器设备。

> **追问 2：为什么要提前 5 分钟刷新 token？不是过期了再刷也行么？**
>
> A：不行，有竞态问题。如果等到精确过期那一刻才刷新，从检测到过期到新 token 拿回来有个时间窗口（比如网络延迟 200ms），这个窗口内如果有请求进来，会用过期 token 去调 API，100% 拿到 401。提前 5 分钟刷新，保证在 token 真正过期前就有新 token 就位，请求永远用有效 token。5 分钟是 buffer，正常刷新 1-2 秒就够了，5 分钟能覆盖网络慢或认证服务器响应慢的情况。

> **追问 3：双重检查锁是什么？为什么需要它？**
>
> A：双重检查锁是一种并发安全的懒初始化模式。在我这里，refreshToken 加了写锁，但进入写锁之前有个时间窗口：多个 goroutine 发现 token 过期，都想去刷新，第一个抢到写锁，其他的排队等。第一个刷完释放锁，第二个进来，如果不做第二次检查，它也会发请求刷新，造成不必要的重复刷新。双重检查就是进入写锁后再检查一次 token 是否已经有效（可能第一个 goroutine 刚刷好了），是的话直接用，不重复请求。这避免了高并发下的"惊群效应"。

> **追问 4：RoundTripper 是什么？你为什么在这里处理 401？**
>
> A：RoundTripper 是 Go 标准库 `http.Client` 的底层传输接口，每个 HTTP 请求都会经过它，相当于 HTTP 层的中间件。我实现了一个 `AuthRoundTripper`，在这里自动注入 Authorization header，拦截 401 响应、触发 token 刷新并重试。选这里的原因是：这是所有请求的必经之路，在这里统一处理鉴权，业务层不需要写任何鉴权代码，完全解耦。对比放在业务层处理，每个 API 调用点都要写 if 401 retry，代码重复而且容易漏。

> **追问 5：如果刷新 token 本身也失败了，怎么处理？**
>
> A：refreshToken 有指数退避重试，重试几次后还失败，就返回 error 往上传。上层 GetToken 收到 error，Handler 收到 error，最终返回给模型的是 ToolResultError "认证失败，请检查配置"。服务不会崩，但这次查询失败了。失败时会有 slog.Error 记录，方便运维排查是不是 OAuth 服务器出问题或者 client_secret 过期了。这是一个"fail fast"的策略，认证失败了不掩盖，直接暴露出来。

### Q1：你的日志方案是怎么设计的？三个库各自是什么作用？

**A：** 三个库各司其职：slog 做结构化日志（Go 1.21 标准库），key-value 格式方便字段过滤；tint 做控制台彩色输出，开发阶段调试直观，文件输出自动关颜色；lumberjack 做日志文件轮转，按大小分割、保留最近 N 个文件、自动压缩，防磁盘打满。

> **追问 1：结构化日志和普通文本日志区别是什么？**
>
> A：普通文本日志是字符串拼的，比如 `"[INFO] request to /api failed with 500 at 2025-01-01"`，要过滤某个接口的错误，得写正则，而且格式不一致很难批量分析。结构化日志是 key-value 格式，每个信息是独立字段，比如 `slog.Error("API failed", "endpoint", "/api", "status", 500, "error", err.Error())`，接日志平台后可以直接用 `endpoint="/api" AND status=500` 过滤，不需要正则，性能好，查询也精准。生产级别的日志系统（ELK、Grafana Loki、Datadog）都原生支持结构化日志。

> **追问 2：AddSource: true 有什么用？**
>
> A：会在每条日志里加上产生这条日志的源文件路径和行号，比如 `source=lifull.go:96`。排查 bug 时，直接跳到对应行，不需要搜关键词，省很多时间。我用了 `filepath.Base(source.File)` 只保留文件名去掉路径，不然路径太长，日志看起来很乱。

> **追问 3：如果线上出了问题，你怎么排查？**
>
> A：先看 slog.Error，里面有 endpoint、status_code、raw_body，基本能判断是我这边还是 LIFULL 的问题。如果需要追一次完整请求的链路，按请求时间窗口过滤日志，把入口日志、工具执行日志、外部调用日志按时间顺序拼起来看。目前缺 requestId 串联，这是一个已知改进点——后续在 HTTP 层生成 UUID requestId，通过 context 透传，每条日志带上这个 ID，就能一行命令查完整链路，比如 `grep requestId=xxx mcp.log`。

> **追问 4：lumberjack 日志轮转是什么意思？为什么要做？**
>
> A：轮转就是：日志文件写到一定大小（比如 100MB）就自动切一个新文件，旧文件压缩存档，保留最近 N 个，更老的删掉。不做轮转的话，日志文件会无限增大，最终把磁盘写满，服务崩溃。lumberjack 把这些封装好了，配置 MaxSize（单文件最大 MB）、MaxBackups（最多保留几个历史文件）、MaxAge（最多保留几天）三个参数，自动处理，不需要写 cron job 清日志。

## 十二、终极追问与回答

**Q：你这个项目最难的地方是什么？**

A：两块。第一是 streamable-http 传输层，SDK 不支持，从零自研了 POST+SSE 双工机制，处理会话绑定、CORS、连接超时清理，对 Go 并发和 HTTP 协议理解要求高；第二是排查 LangGraph + CopilotKit 集成的偶发 bug，消息序列被打乱触发 OpenAI 400，偶发不好复现，加了详细日志才定位到根因，在 reducer 层加过滤修掉了。

> **追问：你说偶发 bug 难排查，具体难在哪？你用了什么方法？**
>
> A：难在两点：一是无法稳定复现，意味着你没办法加个断点直接看，只能靠日志推理；二是跨框架的问题，LangGraph 和 CopilotKit 各自有自己的状态更新机制，交叉点出了问题很难直接从代码看出来。我的方法：第一步先看报错信息，把报错的 API 错误信息完整记下来，搞清楚是什么类型的错误；第二步在最可疑的地方（messages 归并的 reducer）加最详细的日志，把每次更新前后的状态都打出来；第三步等 bug 触发，对比正常和异常的日志差异，找到"孤立 tool 消息"这个特征，然后往上追它的来源。这个过程用了大概半天时间。

---

**Q：这个项目如果让你重构，会改哪些地方？**

A：三点。第一是加 requestId/traceId 透传，现在日志散，有 ID 后一行命令查完整链路；第二是 Agent 状态持久化从 MemorySaver 换成 LibSQL/Postgres，重启不丢会话历史；第三是主数据缓存加版本号校验，目前靠删文件重启更新，加了版本号可以启动时自动检测增量更新。

> **追问：你说的 traceId 透传怎么实现？**
>
> A：在 HTTP 层请求进来的时候，检查是否有 `X-Request-Id` header，有就用它，没有就生成一个 UUID，然后用 `context.WithValue` 把这个 ID 塞进 context，往下传。所有用这个 context 的 slog 调用，把 requestId 作为一个固定字段加上去，比如 `slog.Info("msg", "request_id", ctx.Value("request_id"), ...)`。这样一次请求的所有日志都带同一个 ID，用 `grep request_id=xxx mcp.log` 就能把整条链路的日志捞出来。

**Q：Go 和 TypeScript 各自管什么？为什么这么分？**

A：MCP 服务端用 Go，Agent 层用 TypeScript。Go 适合 I/O 密集型服务，goroutine 模型轻量、并发能力强、编译后单二进制部署简单；TypeScript/Node.js 适合 Agent 编排，LangGraph、LangChain、CopilotKit 都是 JavaScript 优先，生态更成熟，async/await 写异步编排更直观。两边通过 MCP 协议通信，语言隔离清晰，互不干扰。

> **追问：两端联调是怎么做的？怎么确保接口对齐？**
>
> A：本地联调走 stdio 模式，Agent 把 MCP Server 作为子进程启动，两边直接 stdin/stdout 通信，不用启 HTTP 服务，最简单。接口对齐靠 MCP 协议规范：Tool 的参数 schema 是 JSON Schema 格式，Agent 侧用 `MultiServerMCPClient` 自动从 MCP Server 拉工具列表，schema 有变化服务端改了客户端下次连上来就能感知。不用手写 API 文档对齐，协议本身保证了两端的一致性。

---

**Q：MCP 和 OpenAI 的 Function Calling 是什么关系？**

A：Function Calling 是 OpenAI 的工具调用机制，是模型层的能力——模型决定调什么、传什么参数。MCP 是工具托管协议，解决工具怎么注册、怎么发现、怎么执行的问题。两者配合：模型用 Function Calling 触发工具调用，工具实际注册和运行在 MCP Server 里。LangGraph Agent 把 MCP 的工具列表转换成 Function Calling 的 function 定义，模型调 function，Agent 框架把调用路由到 MCP Server 执行。

> **追问：如果不用 MCP，直接把工具写在 Agent 里，有什么区别？**
>
> A：可以，但有两个问题：第一，工具和 Agent 强耦合，换一个 Agent 框架（比如从 LangGraph 换成 Mastra）就要重写所有工具；第二，工具只能被一个 Agent 调，不能共享。用 MCP 的好处是工具服务化：MCP Server 独立部署，任何支持 MCP 协议的客户端都能接入——Claude Desktop、自研 Agent、其他团队的 Agent 都可以用同一套工具，不用重复实现。这就是"工具服务化"的核心价值：一次实现，多端复用。
